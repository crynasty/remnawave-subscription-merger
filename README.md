# Remnawave Subscription Merger

Remnawave Subscription Merger — это реверс-прокси, который располагается перед страницей 
подписки [Remnawave](https://remna.st/). Он объединяет основную и лимитную конфигурации 
подписки пользователя в единый ответ, сохраняя метаданные основной конфигурации.

## Возможности

- Прозрачное проксирование страницы подписки и её ресурсов для браузеров
- Поддержка всех форматов клиентских конфигураций Remnawave
- Сохранение метаданных основной подписки и не связанных с прокси разделов конфигурации
- Fail-open-поведение: при невозможности объединения возвращается исходная основная конфигурация
- Совместимость с альтернативными страницами подписки, возвращающими идентичный набор HTTP-заголовков

## Требования

| Зависимость | Минимальная версия |
|---|---|
| Remnawave | 1.6.0 или новее |

## Подготовка пользователей Remnawave

Для каждого основного пользователя должен существовать соответствующий лимитный 
пользователь. Имя лимитного пользователя формируется с использованием
`LIMITED_PREFIX`:

```text
Primary username: 0123456789
LIMITED_PREFIX: L
Limited username: L_0123456789
```

Используйте короткий `LIMITED_PREFIX`: Remnawave ограничивает полное имя пользователя, включая префикс и `_`, 36 символами.

Основной и лимитный пользователи должны принадлежать разным внутренним сквадам с различными
наборами доступных хостов. Если внутренние сквады содержат повторяющиеся хосты, они будут
продублированы в объединённой конфигурации.

## Переменные окружения

| Переменная | Обязательна | Описание |
|---|---:|---|
| `REMNAWAVE_TOKEN` | Да | API-токен панели Remnawave. Создаётся в **Panel → Settings → API Tokens** |
| `REMNAWAVE_PANEL_URL` | Да | Базовый URL API панели Remnawave |
| `REMNAWAVE_HEADERS` | Нет | Дополнительные HTTP-заголовки для запросов к панели в формате `Key:Value;Key2:Value2` |
| `LIMITED_PREFIX` | Да | Префикс, используемый для формирования имени limited-пользователя. Указывается без символа `_` — merger добавит его автоматически |
| `PROXY_PORT` | Да | Порт, на котором будет слушать merger. В примере используется `3030` |
| `SUBSCRIPTION_PAGE_INTERNAL_URL` | Да | Внутренний URL страницы подписки, на который будут проксироваться входящие запросы |
| `LOG_LEVEL` | Нет | Уровень детализации логов: `DEBUG`, `INFO`, `WARN` или `ERROR`. По умолчанию используется `INFO`; для вывода только ошибок установите `ERROR` |

Пример конфигурации доступен в файле [`.env.example`](.env.example).

## Руководство по установке

1. Создайте новую директорую для merger:

   ```bash
   mkdir /opt/remnawave-subscription-merger && cd /opt/remnawave-subscription-merger
   ```

2. Скачайте шаблон переменных окружения:

   ```bash
   curl -o .env https://raw.githubusercontent.com/crynasty/remnawave-subscription-merger/main/.env.example
   ```

3. Настройте переменные окружения:
   
   ```bash
   nano .env
   ```   

4. Скачайте файл `docker-compose.yml`:

   ```bash
   curl -O https://raw.githubusercontent.com/crynasty/remnawave-subscription-merger/main/docker-compose.yml
   ```  

5. Запустите merger:

   ```bash
   docker compose up -d && docker compose logs -f
   ```

6. В конфигурации реверс-прокси замените `remnawave-subscription-page` на merger.

   Например, при использовании Caddy:

   ```diff
   https://sub.domain.com {
      encode
   -  reverse_proxy * http://remnawave-subscription-page:3010
   +  reverse_proxy * remnawave-subscription-merger:3030
   }

   :443 {
      tls internal
      respond 204
   }
   ```

Примените новую конфигурацию перезапустив используемый вами реверс-прокси.

## Альтернативные страницы подписки

Merger совместим альтернативными страницами подписки Remnawave, возвращающими идентичный 
[subscription-page](https://github.com/remnawave/subscription-page) набор HTTP-заголовков. 

## Практический сценарий использования

Merger позволяет гибко ограничивать трафик: поскольку квота лимитного пользователя 
расходуется только при использовании его хостов, можно задавать отдельные лимиты трафика для выбранных 
внутренних сквадов, не затрагивая основную подписку пользователя.

Использование тега `{{TRAFFIC_USED}}` в именах хостов лимитного пользователя позволяет 
отслеживать потребление трафика в клиентском приложении.
